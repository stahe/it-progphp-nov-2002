    3. Introduzione alla programmazione web in PHP

    3.1. Programmazione PHP

    Ricordiamo qui che PHP è un linguaggio a sé stante e che, sebbene sia utilizzato principalmente nel contesto dello sviluppo di applicazioni web, può essere utilizzato anche in altri contesti. Il documento "PHP by Example" disponibile all'URL http://shiva.istia.univ-angers.fr/~tahe/pub/php/php.pdf fornisce le nozioni di base del linguaggio. Partiamo dal presupposto che abbiate già acquisito padronanza di queste nozioni di base. Utilizziamo un semplice esempio per dimostrare come eseguire un programma PHP su Windows. Il codice seguente è stato salvato come coucou.php.

    <?php
    echo "coucou";
?>

    Questo programma viene eseguito in una finestra del Prompt dei comandi di Windows:

    
dos>"e:\program files\easyphp\php\php.exe" coucou.php
X-Powered-By: PHP/4.3.0-dev
Content-type: text/html
 
coucou

    Si noti che l'interprete PHP invia di default quanto segue:

    • L'interprete PHP è php.exe e si trova normalmente nella directory <php> dell'installazione del software.
    • le intestazioni HTTP X-Powered-By e Content-type:
    • la riga vuota che separa le intestazioni HTTP dal resto del documento
    • il documento costituito in questo caso dal testo scritto dalla funzione echo

    3.2. Il file di configurazione dell'interprete PHP

    Il comportamento dell'interprete PHP è configurato tramite un file di configurazione chiamato php.ini, che si trova, in Windows, all'interno della stessa directory di Windows. Si tratta di un file piuttosto voluminoso; in Windows, per la versione 4.2 di PHP, contiene quasi 1.000 righe, tre quarti delle quali, fortunatamente, sono commenti. Esaminiamo alcune delle impostazioni di configurazione di PHP:

    short_open_tag = On
    consente di includere istruzioni tra i tag <? >. Se impostato su Off, devono essere incluse tra <?php ... >
    asp_tags = Off
    Se impostato su On, consente l'uso della sintassi <% =variabile %> utilizzata da ASP (Active Server Pages)
    expose_php = On
    Abilita l'invio dell'intestazione HTTP X-Powered-By: PHP/4.3.0-dev. Se impostato su Off, questa intestazione viene rimossa.
    error_reporting  =  E_ALL & ~E_NOTICE
    Imposta l'ambito della segnalazione degli errori. In questo caso, verranno segnalati tutti gli errori (E_ALL) eccetto gli avvisi di runtime (~E_NOTICE)
    display_errors = Off
    Se impostata su on, inserisce gli errori nell'output HTML inviato al client. Questi vengono quindi visualizzati nel browser. Si consiglia di impostare questa opzione su off.
    log_errors = On
    Gli errori verranno registrati in un file
    track_errors = On
    memorizza l'ultimo errore verificatosi nella variabile $php_errormsg
    error_log = E:\Program Files\EasyPHP\php\errors.log
    Imposta il file di log degli errori (se log_errors=on)
    register_globals = Off
    Se impostato su On, alcune variabili diventano globali. Considerato una falla di sicurezza.
    default_mimetype = "text/html"
    genera l'intestazione HTTP predefinita: Content-type: text/html
    include_path    =".;E:\Program Files\EasyPHP\php\pear\"
    l'elenco delle directory in cui verranno cercati i file richiesti dalle direttive include o require
    session.save_path = /temp
    la directory in cui verranno salvati i file che memorizzano le varie sessioni attive. Il disco in questione è quello su cui è stato installato PHP. In questo caso, /temp si riferisce a e:\temp

    Questo file di configurazione influisce sulla portabilità del programma PHP. Infatti, se un'applicazione web deve recuperare il valore di un campo C da un modulo web, può farlo in vari modi a seconda che la variabile di configurazione register_globals sia impostata su on o off:

    • off: il valore verrà recuperato tramite $HTTP_GET_VARS["C"] o _GET["C"] o $HTTP_POST_VARS["C"] o $_POST["C"] a seconda del metodo (GET/POST) utilizzato dal client per inviare i valori del modulo
    • on: come sopra, più $C, poiché il valore del campo C è stato reso globale in una variabile con lo stesso nome del campo

    Se uno sviluppatore scrive un programma utilizzando la notazione $C perché il server web/PHP che sta utilizzando ha la variabile register_globals impostata su on, quel programma non funzionerà più se viene spostato su un server web/PHP dove quella stessa variabile è impostata su off. Dovremmo quindi mirare a scrivere programmi che evitino di utilizzare funzionalità dipendenti dalla configurazione del server web/PHP.

    3.3. Configurazione di PHP in fase di esecuzione

    Per migliorare la portabilità di un programma PHP, è possibile impostare autonomamente alcune variabili di configurazione PHP. Queste vengono modificate durante l'esecuzione del programma e solo per quel programma. Due funzioni sono utili in questo processo:

    ini_get("confVariable")
    restituisce il valore della variabile di configurazione confVariable
    ini_set("confVariable", "value")
    imposta il valore della variabile di configurazione confVariable

    Ecco un esempio in cui impostiamo il valore della variabile di configurazione track_errors:

    <?php
     // value of the track_errors configuration variable
    echo "track_errors=".ini_get("track_errors")."\n";
  // change this value
  ini_set("track_errors","off");
   // check
  echo "track_errors=".ini_get("track_errors")."\n";
?>

    Una volta eseguito, si ottengono i seguenti risultati:

    E:\data\serge\web\php\poly\intro>"E:\Program Files\EasyPHP\php\php.exe" conf1.php
Content-type: text/html

track_errors=1
track_errors=off

    Il valore della variabile di configurazione track_errors era inizialmente 1 (~on). Lo impostiamo su off. Si noti che se la nostra applicazione si basa su determinati valori delle variabili di configurazione, è prudente inizializzarli all'interno del programma stesso.

    3.4. Contesto di esecuzione per gli esempi

    Gli esempi in questo documento verranno eseguiti con la seguente configurazione:

    • PC con sistema operativo Windows 2000
    • Server Apache 1.3
    • PHP 4.3

    La configurazione del server Apache è specificata nel file httpd.conf. Le righe seguenti indicano ad Apache di caricare PHP come modulo integrato e di inoltrare qualsiasi richiesta di un documento con determinate estensioni di file — tra cui .php — all'interprete PHP. Questa è l'estensione predefinita che useremo per i nostri programmi PHP.

    LoadModule php4_module "E:/Program Files/EasyPHP/php/php4apache.dll"
AddModule mod_php4.c
AddType application/x-httpd-php .phtml .pwml .php3 .php4 .php .php2 .inc

    Inoltre, abbiamo definito un alias "poly" per Apache:

    Alias "/poly/" "e:/data/serge/web/php/poly/"
<Directory "e:/data/serge/web/php/poly">
  Options Indexes FollowSymLinks Includes
  AllowOverride All
  # Order allow,deny
  Allow from all
</Directory>

    Chiamiamo il percorso e:/data/serge/web/php/poly <poly>. Se vogliamo richiedere il documento doc.php dal server Apache utilizzando un browser, useremo l'URL http://localhost/poly/doc.php. Il server Apache riconoscerà l'alias poly nell'URL e assocerà quindi l'URL /poly/doc.php al documento <poly>\doc.php.

    La soluzione di collocare il codice PHP e HTML in file separati verrà adottata in seguito. Essa offre diversi vantaggi:

    Tuttavia, questa soluzione presenta uno svantaggio: invece di richiedere il caricamento di un unico documento, richiede il caricamento di più documenti, il che può comportare una perdita di prestazioni.

    3.6.1. tramite un POST

    Si consideri il seguente modulo in cui l'utente deve fornire due informazioni: un nome e un'età.

    Una volta compilati i campi Nome ed Età, l'utente fa clic sul pulsante Invia. I valori del modulo vengono quindi inviati al server. Il server restituisce il modulo insieme a un array che elenca i valori ricevuti:

    Il browser richiede il modulo dall'applicazione nomage.php seguente:

    <?php
   // do we have the expected parameters?
  $post=isset($_POST["txtNom"]) && isset($_POST["txtAge"]);
  if($post){
    // retrieve the txtNom and txtAge parameters "posted" by the client
    $nom=$_POST["txtNom"];
    $age=$_POST["txtAge"];
  } else {
      $nom="";
    $age="";
  }//if
   // page display
  include "nomage-p1.php";
?>

    Alcune spiegazioni:

    • Un campo di un modulo HTML chiamato "field" può essere inviato al server utilizzando il metodo GET o il metodo POST. Se inviato tramite il metodo GET, il server può recuperarlo dalla variabile $_GET["field"]; se inviato tramite il metodo POST, può essere recuperato dalla variabile $_POST["field"].
    • L'esistenza di un dato può essere verificata utilizzando la funzione isset(data), che restituisce true se il dato esiste, false in caso contrario.
    • L'applicazione nomage.php crea tre variabili: $name per il nome del modulo, $age per l'età e $post per indicare se i valori sono stati "inviati" o meno. Queste tre variabili vengono passate alla pagina nomage-p1.php. Si noti che, sebbene questa pagina partecipi alla generazione della risposta al client, il client non ne è a conoscenza. Dal punto di vista del client, è l'applicazione nomage.php a rispondere.
    • La prima volta che un client richiede l'applicazione nomage.php, $post viene impostato su false. Questo perché, durante questa prima chiamata, nessun valore del modulo viene inviato al server.

    La pagina nomage-p1.php è la seguente:

    <html>
  <head>

  </head>

       <h3>Un formulaire Web</h3>

           <form name="frmPersonne" method="post">

    Poiché l'attributo action del tag non è definito, il browser invierà i dati del modulo all'URL da cui li ha richiesti, ovvero l'applicazione nomage.php.

    Distinguiamo i due casi di chiamata all'applicazione nomage.php:

    1. Questa è la prima volta che l'utente la chiama. L'applicazione nomage.php chiama quindi l'applicazione nomage-p1.php, passandole i valori ($nom, $age, $post) = ("", "", false). L'applicazione nomage-p1.php visualizza quindi un modulo vuoto.
    2. L'utente compila il modulo e clicca sul pulsante Invia. I valori del modulo (txtName, txtAge) vengono quindi "inviati" (method="post" in <form>) all'applicazione nomage.php (attributo action non definito in <form>). L'applicazione nomage.php calcola ($name, $age, $post) = (txtName, txtAge, true) e li trasmette all'applicazione nomage-p1.php, che quindi visualizza un modulo precompilato insieme alla tabella dei valori recuperati.

    3.7. Recupero delle intestazioni HTTP inviate da un client web

    Quando un browser effettua una richiesta a un server web, invia una serie di intestazioni HTTP. A volte è utile poter accedere a queste informazioni. Possiamo iniziare utilizzando l'array associativo $_SERVER. Questo contiene varie informazioni fornite dal server web, tra cui, tra le altre cose, le intestazioni HTTP inviate dal client. Consideriamo il seguente programma, che visualizza tutti i valori dell'array $_SERVER:

    <?php
     // displays variables related to the web server
   // send simple text
  header("Content-type: text/plain");
   // associative array path $_SERVER
     reset($_SERVER);
     while (list($clé,$valeur)=each($_SERVER)){
      echo "$clé : $valeur\n";
    }//while
?>

    Salviamo questo codice in headers.php e richiediamo questo URL utilizzando un browser:

    Otteniamo una serie di informazioni, tra cui le intestazioni HTTP inviate dal browser. Si tratta dei valori associati alle chiavi che iniziano con HTTP. Analizziamo alcune delle informazioni ottenute sopra:

    HTTP_ACCEPT
    tipi di documento accettati dal client web
    HTTP_ACCEPT_CHARSET
    set di caratteri accettati nei documenti
    HTTP_ACCEPT_ENCODING
    tipi di codifica accettati per i documenti
    HTTP_ACCEPT_LANGUAGE
    tipi di lingua accettati per i documenti
    HTTP_CONNECTION
    tipo di connessione con il server. Keep-Alive: il server deve mantenere aperta la connessione dopo aver inviato la risposta
    HTTP_KEEP_ALIVE
    ? durata massima della connessione
    HOST
    macchina host interrogata dal client
    HTTP_USER_AGENT
    identità del client
    REMOTE_ADDR
    indirizzo IP del client
    REMOTE_PORT
    porta di comunicazione utilizzata dal client
    SERVER_PROTOCOL
    protocollo HTTP utilizzato dal server
    METODO_RICHIESTA
    metodo di richiesta utilizzato dal client (GET o POST)
    QUERY_STRING
    query ?param1=val1&param2=val2&... aggiunta all'URL richiesto (metodo GET)

    Modificando leggermente il codice del programma precedente, possiamo recuperare solo le intestazioni HTTP:

     reset($_SERVER);
     while (list($clé,$valeur)=each($_SERVER)){
      // header HTTP ?
    if(strtolower(substr($clé,0,4))=="http")
          echo substr($clé,5)." : $valeur\n";
    }//while
?>

    3.10. Monitoraggio delle sessioni

    3.10.1. Il problema

    Un'applicazione web può consistere in diversi scambi di moduli tra il server e il client. Il processo funziona come segue:

    Fase 1

    1. Il client C1 stabilisce una connessione con il server ed effettua la sua richiesta iniziale.
    2. Il server invia il modulo F1 al client C1 e chiude la connessione aperta nel passaggio 1.

    Fase 2

    1. Il client C1 compila il modulo e lo rinvia al server. A tal fine, il browser apre una nuova connessione con il server.
    2. Il server elabora i dati del modulo 1, ne ricava l'informazione I1, invia il modulo F2 al client C1 e chiude la connessione aperta nel passaggio 3.

    Fase 3

    1. Il ciclo dei passaggi 3 e 4 si ripete nei passaggi 5 e 6. Al termine del passaggio 6, il server avrà ricevuto due moduli, F1 e F2, e avrà calcolato le informazioni I1 e I2 da essi.

    Il problema in questione è: in che modo il server tiene traccia delle informazioni I1 e I2 associate al client C1? Questo problema è chiamato tracciamento della sessione del client C1. Per comprenderne la causa principale, esaminiamo il diagramma di un'applicazione server TCP-IP che serve più client contemporaneamente:

    In una classica applicazione client-server TCP-IP:

    • il client stabilisce una connessione con il server
    • scambia dati con il server tramite questa connessione
    • la connessione viene chiusa da una delle due parti

    I due punti chiave di questo meccanismo sono:

    1. viene creata una singola connessione per ogni client
    2. questa connessione viene utilizzata per l'intera durata del dialogo tra il server e il suo client

    Ciò che permette al server di sapere in ogni momento con quale client sta interagendo è la connessione — o, in altre parole, il "canale" — che lo collega al suo client. Poiché questo canale è dedicato a un client specifico, tutto ciò che passa attraverso questo canale proviene da quel client, e tutto ciò che viene inviato attraverso questo canale raggiunge lo stesso client.

    Il meccanismo client-server HTTP segue il modello precedente, con l'eccezione che il dialogo client-server è limitato a un singolo scambio tra il client e il server:

    • il client apre una connessione al server ed effettua la sua richiesta
    • il server invia la sua risposta e chiude la connessione

    Se al tempo T1, un client C effettua una richiesta al server, ottiene una connessione C1 che verrà utilizzata per il singolo scambio richiesta-risposta. Se, al tempo T2, questo stesso client effettua una seconda richiesta al server, otterrà una connessione C2 diversa dalla connessione C1. Per il server, non vi è quindi alcuna differenza tra questa seconda richiesta dell’utente C e la sua richiesta iniziale: in entrambi i casi, il server tratta il cliente come un nuovo cliente. Affinché vi sia un collegamento tra le diverse connessioni del cliente C al server, il cliente C deve essere “riconosciuto” dal server come un “cliente abituale” e il server deve recuperare le informazioni in suo possesso su tale cliente abituale.

    Immaginiamo un'agenzia governativa che opera come segue:

    • C'è una sola coda
    • Ci sono diversi sportelli di servizio. Pertanto, è possibile servire più clienti contemporaneamente. Quando uno sportello si libera, un cliente lascia la coda per essere servito a quello sportello
    • Se questa è la prima visita del cliente, l'addetto allo sportello gli consegna un biglietto con un numero. Il cliente può porre una sola domanda. Una volta ricevuta la risposta, deve lasciare lo sportello e tornare in fondo alla fila. L'addetto allo sportello registra le informazioni del cliente in un fascicolo contrassegnato dal numero.
    • Quando è di nuovo il suo turno, il cliente potrebbe essere servito da un addetto diverso rispetto alla volta precedente. L'addetto chiede il suo gettone e recupera il fascicolo con il numero del gettone. Ancora una volta, il cliente fa una richiesta, riceve una risposta e le informazioni vengono aggiunte al suo fascicolo.
    • E così via... Nel corso del tempo, il cliente riceverà le risposte a tutte le sue richieste. Il collegamento tra le diverse richieste viene mantenuto tramite il gettone e la scheda ad esso associata.

    Il meccanismo di tracciamento della sessione in un'applicazione web client-server funziona in modo simile all'esempio precedente:

    • Al momento della prima richiesta, al client viene rilasciato un token dal server web
    • presenterà questo token ad ogni richiesta successiva per identificarsi

    Il token può assumere varie forme:

    • un campo nascosto in un modulo
      • il client effettua la sua prima richiesta (il server la riconosce perché il client non ha alcun token)
      • Il server invia la sua risposta (un modulo) e inserisce il token in un campo nascosto al suo interno. A questo punto, la connessione viene chiusa (il client esce dalla sessione con il proprio token). Il server potrebbe avere delle informazioni associate a questo token.
      • Il client effettua una seconda richiesta inviando nuovamente il modulo. Il server recupera il token dal modulo. Può quindi elaborare la seconda richiesta del client accedendo, tramite il token, alle informazioni calcolate durante la prima richiesta. Nuove informazioni vengono aggiunte al file associato al token, una seconda risposta viene inviata al client e la connessione viene chiusa per la seconda volta. Il token è stato reinserito nel modulo di risposta in modo che l'utente possa presentarlo durante la sua prossima richiesta.
      • e così via...

    Lo svantaggio principale di questa tecnica è che il token deve essere inserito in un modulo. Se la risposta del server non è un modulo, non è più possibile utilizzare il metodo del campo nascosto.

    • Il metodo del cookie
      • Il client effettua la sua prima richiesta (il server la riconosce perché il client non ha alcun token)
      • Il server risponde aggiungendo un cookie alle intestazioni HTTP. Ciò avviene utilizzando il comando HTTP Set-Cookie:

    Set-Cookie: param1=valore1;param2=valore2;....

    dove param1, param2, ecc. sono i nomi dei parametri e i rispettivi valori. Tra i parametri ci sarà il token. Molto spesso, nel cookie viene incluso solo il token, mentre il server memorizza le altre informazioni nella cartella associata al token. Il browser che riceve il cookie lo memorizzerà in un file sul disco. Dopo la risposta del server, la connessione viene chiusa (il client esce dalla sessione con il proprio token).

    • (continua)
      • Il client effettua la sua seconda richiesta al server. Ogni volta che viene effettuata una richiesta a un server, il browser controlla tra tutti i cookie in suo possesso per vedere se ne ha uno proveniente dal server richiesto. In tal caso, lo invia al server, sempre sotto forma di comando HTTP: il comando Cookie, che ha una sintassi simile a quella del comando Set-Cookie utilizzato dal server:

    Cookie: param1=valore1;param2=valore2;....

    Tra le intestazioni HTTP inviate dal browser, il server troverà il token che gli permette di riconoscere il client e recuperare le informazioni ad esso associate.

    Questa è la forma di token più comunemente utilizzata. Presenta un unico svantaggio: un utente può configurare il proprio browser in modo da rifiutare i cookie. Tali utenti non potranno quindi accedere alle applicazioni web che utilizzano i cookie.

    • Riscrittura dell'URL
      • Il client effettua la sua prima richiesta (il server la riconosce perché il client non ha alcun token)
      • Il server invia la sua risposta. Questa risposta contiene dei link che l'utente deve utilizzare per continuare a utilizzare l'applicazione. Nell'URL di ciascuno di questi link, il server aggiunge il token nella forma URL;token=valore.
      • Quando l'utente clicca su uno dei link per continuare a utilizzare l'applicazione, il browser invia una richiesta al server web, includendo l'URL richiesto (URL;token=value) nelle intestazioni HTTP. Il server è quindi in grado di recuperare il token.

    3.10.2. L'API PHP per il tracciamento delle sessioni

    Presenteremo ora i principali metodi utili per il tracciamento delle sessioni:

    session_start()
    avvia la sessione a cui appartiene la richiesta corrente. Se la richiesta non faceva ancora parte di una sessione, ne viene creata una.
    session_id()
    identificatore della sessione corrente
    $_SESSION[$var]
    dizionario che memorizza i dati della sessione. Accessibile in lettura e scrittura
    session_destroy()
    elimina i dati contenuti nella sessione corrente. Questi dati rimangono disponibili per lo scambio client-server in corso, ma non saranno disponibili durante lo scambio successivo.
